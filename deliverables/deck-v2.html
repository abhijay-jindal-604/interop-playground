The problem

A failed presentation is one opaque error; the cause sits in a message two hops earlier.

What the verifier says Inji Verify: invalid
ERR_SIGNATURE_VERIFICATION_FAILED
"getX509CertChain(...) must not be null"
→
Where the cause is The walt.id credential, issued two hops earlier, carries no x5c chain in its SD-JWT header, and Inji Verify requires one (gap G-55).
→
Why it is slow today Issuer, wallet and verifier come from different teams. Nobody sees all the messages of one journey in one place, so each failure is debugged by hand.
Speaker: "When a credential fails at a verifier, you get one code. The cause is in an earlier message that no single component shows." Source: run 01M5B6KNNY7DC3YK3CR0ETNBN9, report docs/reports/01M5B6KNNY7DC3YK3CR0ETNBN9.md (live, 2026-10-20); docs/overview.md "The problem".

The solution

Pick three roles, run the real protocols, inspect every payload, get a report.

SelectIssuer, wallet, verifier, format, mode. Impossible combinations are greyed out with the reason and the gap ID.
→
RunOpenID4VCI 1.0 pre-authorized issuance and OpenID4VP 1.0 cross-device presentation, live against Inji in Docker.
→
InspectEvery HTTP exchange, decoded SD-JWT disclosures and JOSE headers; each hop labelled full / partial / none capture.
→
Report and fixPer-run JSON and Markdown report; a diagnosis card, and a one-click fix-it re-run when the fix is proven.

Two formats live: SD-JWT VC (dc+sd-jwt) and W3C VC JSON-LD (ldp_vc). Verifier labels Valid, Invalid and Valid-but-Expired.

Speaker: "Pick an issuer, a wallet and a verifier; we run OpenID4VCI and OpenID4VP for real and hand you a report." Say "two formats live"; mDoc was cut (docs/decisions.md 2026-10-20). Sources: README "What it does", "Formats and labels"; screens in docs/design.md.
4 / 9

How it works

One backend drives every role and records each exchange in an event log the UI replays.

Speaker: "The backend makes every outbound call itself; the wallet's inbound legs pass through an allowlisting gateway. Every event is redacted, persisted, then streamed to the UI over Server-Sent Events, so a finished run replays exactly." Sources: README "Architecture"; docs/architecture.md (four diagrams: components, data flow of one run, issuance and presentation sequence, fix-it derive flow).

The original angle: fix-it re-runs

We do not only diagnose: we prove the fix by re-running with exactly one change.

Parentwalt.id → reference wallet → Inji Verify: FAIL
run 01M5B6KNNY7DC3YK3CR0ETNBN9
→
DiagnosisFP-01, exact match, gap G-55. One offer: KNOB-01 absent → present. No button when the cause is uncertain.
→
ChildSame run, one knob changed: PASS, classified fixed.
run 01M5B6M723AQ7T818D36816PRV

"Changing only waltid.sdjwt.x5c from absent to present makes it pass."

Speaker: "A diagnosis with a proven fix gets one button. One knob changes, the run repeats, and the result proves the fix." Proven live on 2026-10-20. Technology stack

TypeScript backend and UI, real Inji services, every image pinned.

Backend Node 22, TypeScript, Fastify 5, better-sqlite3 event log
UI React 18, Vite 7, React Router, Mermaid sequence diagrams, plain CSS tokens (light and dark)
Live data REST commands, Server-Sent Events (no WebSocket); OpenAPI 3.1 contract

Inji stack Inji Certify, Inji Verify, Mimoto, Inji Web 1.0.0-alpha.1; eSignet 1.8.0; walt.id 1.1.0 as an external peer
Libraries JVM sidecar (Gradle) with the Inji Kotlin libraries (built; not used by v1 flows)
Ops and tests Docker Compose, one scripts/up.sh, digests in versions.lock; Vitest, Playwright, axe-core, GitHub Actions CI
