The problem

A failed presentation is one opaque error at the last hop. The cause sits two hops earlier.

Issuer

walt.id issuer-api2

issues SD-JWT VC
Where the cause is

The credential header carries the issuer key without an x5c certificate chain, which Inji Verify requires (gap G-55).

Wallet

Playground reference wallet

presents over OpenID4VP

Holds the credential and presents it. Nothing here fails, so nothing here looks wrong.

Verifier

Inji Verify

Invalid
ERR_SIGNATURE_VERIFICATION_FAILED
"getX509CertChain(...) must not be null"
←Nothing at the verifier points back to the issuer. Today the trace is done by hand.

Different teams

Issuer, wallet and verifier are built and run by different teams and vendors.

No single view

No component shows all the messages of one credential journey in one place.

Debugged by hand

Each failure is traced by hand, and the fix is guessed rather than shown to work.

What we built

Pick three roles, run the real protocols, read every message.

1
SelectIssuer, wallet, verifier, format and mode. Combinations that cannot work are greyed out with the reason and a gap ID.
2
RunOpenID4VCI 1.0 pre-authorized issuance and OpenID4VP 1.0 cross-device presentation, live against Inji in Docker.
3
InspectEvery HTTP exchange, decoded SD-JWT disclosures and JOSE headers. Each hop says if its capture is full, partial or none.
4
Report and fixA JSON and Markdown report per run, a diagnosis in plain words, and a one-click fix-it re-run when the fix is proven.

How it works

One backend drives every role and writes each exchange to a log the UI replays.

Docker network, digest-pinned
  • Inji Certify 1.0.0-alpha.1
  • Inji Verify 1.0.0-alpha.1
  • Mimoto, Inji Web
  • eSignet 1.8.0
  • walt.id issuer 1.1.0 (peer)
Capture is orchestration

The backend makes every outbound call itself; each hop is labelled full, partial or none.

Persist, then publish

Each event is stored before it is streamed, so a finished run replays exactly.

Immutable runs

A fix-it re-run is a derived RunSpec with one knob changed and a link to its parent.

Closed by default

Inji services publish no ports; the gateway is the only listener and denies admin paths.

Who it is for, and what it changes

For anyone who must make Inji work with something it did not ship with.

Who it is for
Inji and MOSIP developers

See where a change breaks interop, with the exact exchange and the spec clause.

Wallet, issuer and verifier vendors

Test against real Inji services before integrating; the walt.id issuer is the worked example.

Country ID programmes and integrators

Check which combinations work, with evidence, before a rollout.

Conformance and QA teams

Repeatable runs from digest-pinned images and fixture credentials for each label.

What it changes
From one error code to the cause

The failing exchange, its decoded payload and a matched cause on one screen.

From a guessed fix to a proven one

A fix is shown to work by a re-run that changes only that setting.

From anecdotes to evidence

Bug reports that carry the run, the messages and the spec clause.

Roadmap

From one proven fix to a shared compatibility record.

The first column is shipped. The other two are planned work, listed in the README as not in v1.

Shipped in v1

Live on the bundle
  • Two formats, SD-JWT VC and JSON-LD, issued and presented
  • Three issuers: Inji Certify, walt.id, a fixture issuer
  • Inspector and reports for every run
  • Fix-it: one fingerprint, one knob, proven

Next

Wider coverage
  • More adapters: the Inji JVM wallet, Inji Web, the phone wallet, walt.id and EUDI verifiers
  • mDoc (mso_mdoc), cut from v1
  • More fingerprints and knobs for fix-it
  • Tamper mode and suites

Later

Back to the ecosystem
  • Interop matrix across vendors, from the same runs
  • Nightly CI against the Collab sandbox
  • Issue drafts filed upstream with their evidence
  • Fixes contributed to the Inji repositories

The same runs that prove one fix today can feed a cross-vendor compatibility record: every cell a run, every run a report.
